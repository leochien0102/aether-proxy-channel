## 改动

- `.github/workflows/promote.yml`：
  - fetch `tools/channel/build.py` 提前到 Makefile 元数据获取之后，并
    `from channel.build import canonical_version`——与 RC workflow 共用同一条
    canonical 规则（同一 RC commit，规则必然一致）；
  - 包版本检查从 `v != base + '-r' + rev` 改为 `canonical_version(base, rev, v)`：
    接受真实发布的两种渲染（标准包 `-<release>` 如 `0.6.3-1`、`luci.mk` 包
    `-r<release>` 如 `0.6.3-r1`），原样采用文件名版本，不再假设 `-r`；
  - compatibility 处理新增终点步 fail-fast：链的 `steps[-1].version` 必须等于
    本 RC 构建的 aether-proxy canonical version，先于任何 bridge 字节下载；
  - 其余 T11.16 行为保留：rc-manifest 带 `compatibility` 绑定时资产集 22→23、
    绑定名校验；每步必须 ipk+apk；逐资产 sha256/size 校验（目标步 = RC 自身
    noarch 产物取 aarch64_generic 字节，历史步 = 既有 stable 按名下载，皆无则
    明确报错立即失败）；`bridge/` + `GITHUB_ENV` 传递 `COMPATIBILITY_FILE`；
    preflight 与 `scripts/publish.sh` 用同一份输入；
  - 不 checkout app 源码、不执行 SDK/make/编译（app 侧 contract 测试继续断言）。
- `README.md`：T11.16 节补版本规范（canonical version、两种渲染、tag 规范区别）
  与「app 尚未登记任何链」的现状；终点步 fail-fast 说明。
- `scripts/publish.sh` **无改动**；`AETHER_PROXY_REF`、版本、keys 未动。

## 版本规范要点（返工意见 1/3）

- canonical version = 包文件名里的版本串 = 包管理器报告的已安装版本；manifest、
  compatibility 步骤、设备比较全部使用，不从 Makefile 拼装。
- 真实渲染（h28k-test/pkg061-063 实物 + 0.6.3 经 build.py 成功发布 → 同包
  ipk/apk 同串）：aether-proxy `0.6.3-1`、aether-xray `26.10.31-1`、
  chinadns-ng `2025.08.09-1`、luci-app `0.6.3-r1`（luci.mk）、i18n 动态版本无
  release。
- 正式 tag `v<version>-r<release>` 是 tag 规范，经 rc-manifest `target_tag` 单独
  绑定；兼容终点步 == manifest aether-proxy current version == RC 构建版本 ==
  设备安装串；release 后缀精确匹配（设备端 `exact-release-alias` 冻结）。
