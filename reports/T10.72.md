### 3. 本地 SDK 实际构建

**实际构建了 24.10.8 的 x86_64 和 aarch64_generic 两个 ipk，不是引用 CI 结果。**

没有在共享 SDK 中运行 make。把已有 x86_64 SDK 归档解包到本卡 `.local/sdk-x86_64`；ARM 使用官方 24.10.8 armsr/armv8 SDK，解包到 `.local/sdk-aarch64_generic`，其包架构为 aarch64_generic。ARM SDK 与官方 `sha256sums` 比对通过：

SDK 准备步骤：

- 把本卡 `aether-xray/` 复制到两个 SDK 的 `package/`。
- 把共享 SDK 已有的 `feeds/base/package/system/ca-certificates/` 只读复制到本卡 SDK 的 `package/`，仅用于满足 `ca-bundle` 依赖，不是引入仓库产品代码。
- 把已核对的 Go 归档及 Xray 源码归档复制到两个 SDK 的 `dl/`。
- 每个 SDK 的初始 `.config` 为 `CONFIG_PACKAGE_aether-xray=m` 与 `CONFIG_PACKAGE_ca-bundle=y`，随后执行 defconfig。
- HOME、TMPDIR 均设为本卡 `.local/` 下的目录，避免测试写入其他仓库或共享 SDK。


## 场景对照

任务卡没有独立编号的「测试」场景，按「验证」和要求逐项对应：

| 场景 | 本地检查/断言 | 如何证明 |
|---|---|---|
| 包名、版本、release、纯上游 | recipe identity / unpatched upstream source；源码 hash / archive go.mod 逐字节核对 | 旧包名、错版本、错 hash 或增加 patches 均不通过 |
| workflow 无旧构建/检查路径 | 所有 workflow 无小写 xray-core，路径、PACKAGES、ipk/apk 模式逐项断言 | 遗漏旧构建路径、旧包选择或漏改包存在性检查会失败 |
| x64 提取/版本检查使用新二进制 | 原样执行 YAML 的 x64 run 块，退出 0 | 若取旧产物名或执行 usr/bin/xray，真实新包中不存在该文件，检查会失败 |
| bump 只改新 Makefile、隔离旧分支 | 新 namespace、git add 仅新 Makefile、标题/正文及无删除命令检查 | 旧 namespace、全量暂存或旧 PR 名称会失败；未执行远端开 PR/推送 |
| 两架构实际构建和路径 | 两个 SDK make 退出 0；tar 包元数据、唯一文件路径、可执行位、ELF machine 断言 | 错包名、错架构或仍安装 xray 都无法通过 |
| gate 保留原 golden 脚本 | workflow 原脚本路径断言；实际包二进制跑 pinned 脚本 17/17 | 本地确认候选二进制可接受该 ref 的全部 golden，不以 CI 替代 |
| AETHER_PROXY_REF 不动 | 与 HEAD 的原文件逐字节比对 | 改动 ref 会失败 |
| 旧 manifest 历史保留 | publish/build 代码未修改，没有操作 manifest 或发布资产 | 本卡不触碰既有保留逻辑；未做线上发布行为验收 |
